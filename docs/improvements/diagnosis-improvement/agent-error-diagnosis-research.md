# Agent 错误诊断方法调研

聚焦：从 Session 日志中定位问题，生成诊断报告。

---

## 诊断方法的两大流派

| 流派 | 核心思想 | 优点 | 缺点 |
|------|---------|------|------|
| **规则诊断** | 用确定性算法从日志中提取特征、计算指标、匹配模式 | 可解释、低成本、不依赖模型 | 只能检测已知模式 |
| **LLM 诊断** | 让大模型阅读日志，输出分析结论 | 灵活、能理解复杂场景 | 成本高、可能幻觉 |

实际系统中两者通常结合：规则做初筛和特征提取，LLM 做综合分析和结论生成。

---

## 第一部分：规则诊断方法

### 1.1 时序特征提取

从日志中计算可量化的指标，是最基础的规则诊断。

**当前项目已做的：**

| 特征 | 计算方法 | 用途 |
|------|---------|------|
| 工具耗时 | `ended_at - started_at` | 发现慢工具 |
| 阶段耗时 | 按 Skill/用户消息划分阶段 | 定位哪个阶段慢 |
| 空闲时间 | 事件间隔 ≥ 10min | 区分人慢还是工具慢 |
| 错误标记 | `is_error` 字段 | 发现失败调用 |
| 高频调用 | 同工具计数 ≥ 10 | 发现重复/循环 |

**可补充的（来自 AgentProcessBench）：**

| 特征 | 计算方法 | 用途 |
|------|---------|------|
| 步骤质量分 | 参数合理性 + 结果被引用 + 执行时长 | 每个步骤打分，找低分点 |
| 工具成功率 | 成功次数 / 总次数 | 识别问题工具 |
| 重试次数 | 相同参数连续调用次数 | 发现错误重试循环 |

### 1.2 依赖图构建

工具调用不是独立的，后一步经常依赖前一步的结果。

**方法（来自 AgentTrace / GraphTracer）：**

```
tool_result A ──引用──> tool_use B
     │                      │
     └──── 构建依赖边 ──────┘
```

**具体做法：**
1. 扫描 tool_result 的 content 文本
2. 正则匹配是否包含前面 tool_use 的返回值特征（如文件路径、命令输出片段）
3. 建立 `depends_on` 关系

**用途：**
- 错误传播：工具 A 出错 → 工具 B 用了 A 的结果 → B 也出错
- 根因定位：从最终错误反向追溯到最初出错的工具
- 孤立检测：工具结果未被任何后续步骤引用（可能是无用调用）

### 1.3 阶段划分与类型标注

**当前项目做的：**
- 按 Skill 调用分阶段（高置信度）
- 或按用户消息分阶段（中置信度）

**可补充的（来自 STAR）：**

给阶段打类型标签，帮助理解问题性质：

| 阶段类型 | 特征 | 典型问题 |
|---------|------|---------|
| 规划阶段 | Skill/Agent 调用密集 | 目标理解错误、分解不合理 |
| 执行阶段 | Bash/Read/Edit 密集 | 命令错误、文件操作失败 |
| 验证阶段 | 测试/检查类调用 | 验证逻辑不完善 |
| 修复阶段 | Edit 后紧跟测试 | 修复不彻底 |

**分类方法：**
- 统计阶段内各类工具占比
- 或基于 tool_name 规则匹配

### 1.4 模式检测

从时序中发现特定的错误模式。

**可检测的模式：**

| 模式 | 定义 | 示例 |
|------|------|------|
| 高频重复 | 相同工具+相同参数，3次以上 | 死循环重试 |
| 失败-重试-失败 | error → 相同调用 → error | 错误未修复就重试 |
| 长空闲后失败 | idle ≥ 10min → 首次调用 error | 人回来后第一步就错 |
| 结果未使用 | tool_result 后无引用 | 多余调用 |
| 错误传播链 | error → depends_on → error | 级联失败 |

## 第二部分：LLM 诊断方法

### 2.1 输入形式

**当前项目做的：**
- 提取摘要（工具名、耗时、参数片段）
- 拼成 Markdown 表格
- 截断到 60k 字符

**可改进的（来自 Phoenix / Langfuse）：**

| 输入形式 | 做法 | 适用场景 |
|---------|------|---------|
| 结构化 JSON | 保留原始字段，不转文本 | 让 LLM 自己提取关键信息 |
| 完整 trace | 不截断，给完整 input/output | 需要分析具体参数时 |
| 差异对比 | 给"期望结果"和"实际结果" | 明确失败场景 |

**关键权衡：**
- 摘要 vs 完整：摘要省 token 但丢细节，完整贵但能深度分析
- 文本 vs 结构化：LLM 读文本更自然，但结构化便于程序化处理

### 2.2 Prompt 策略

**当前项目做的：**
- 固定模板：执行概要 + 主要问题 + 建议
- 要求引用具体数字

**可改进的（来自 Reflexion / Self-Debug）：**

| 策略 | 做法 | 效果 |
|------|------|------|
| 角色设定 | "你是一位调试专家" | 提升分析专业性 |
| 分步思考 | "先列出所有错误，再分析根因，最后给建议" | 减少幻觉，提高可解释性 |
| 反思验证 | "检查你的分析是否与原始数据一致" | 自纠错 |
| 少样例 | 给 2-3 个分析示例 | 指导输出格式和深度 |

### 2.3 人机结合

**纯自动的问题：**
- LLM 可能分析错误但 confident
- 复杂场景需要人确认

**可做的（来自 Langfuse Playground）：**

| 交互方式 | 做法 |
|---------|------|
| 可点击定位 | 报告中的工具名可点击跳转到原始日志 |
| 确认/反馈 | 人对 LLM 分析打 ✓/✗，用于改进 |
| 迭代深挖 | 人指出"关注这个工具"，LLM 专门分析 |

## 第三部分：可视化辅助

可视化本身不是诊断，但帮助人快速理解问题位置。

### 3.1 甘特图（当前项目已有）

展示：时间轴上的工具调用、阶段划分、耗时分布。

**可增强的：**
- 颜色标记：error 标红、warning 标黄
- 依赖箭头：显示工具间的依赖关系
- 点击展开：点击工具显示完整 input/output

### 3.2 因果图（来自 AgentTrace）

展示：工具节点 + 依赖边，错误传播路径高亮。

```
[Read A] ──错误──> [Bash B] ──依赖──> [Edit C]
   ↑                                     │
   └──────── 根因在此 ──────────────────┘
```

### 3.3 阶段对比图

展示：多个阶段的关键指标对比，快速发现异常阶段。

| 阶段 | 工具数 | 错误数 | 耗时 | 质量分 |
|------|-------|-------|------|-------|
| 阶段 1 | 5 | 0 | 2m | 85 |
| 阶段 2 | 12 | 3 | 15m | 42 ← 异常 |

## 第四部分：推荐实现路径

结合当前项目架构，建议分阶段实现：

### 阶段 1：规则层增强（1-2 周）

**目标：不碰 LLM，纯规则发现更多问题。**

1. **步骤质量评分**
   ```python
   quality_score = (
       (参数是否合理 ? 25 : 0) +
       (结果是否被引用 ? 25 : 0) +
       (耗时是否过长 ? 25 : 0) +
       (是否报错 ? 25 : 0)
   )
   ```

2. **模式检测**
   - 高频重复：相同工具+参数，3次以上
   - 结果未使用：scan 后续 5 条，无引用则标记

3. **依赖图简单版**
   - 只检测 Bash/Read 的结果是否被 Edit 引用
   - 用字符串匹配，不追求完整图

### 阶段 2：LLM 层增强（2-4 周）

**目标：让 LLM 诊断更准确。**

1. **结构化输入**
   - 除文本摘要外，给 LLM 一个 `problems` 数组（规则检测出的可疑点）
   - LLM 优先分析这些可疑点

2. **分步 Prompt**
   ```
   Step 1: 列出所有 detected problems
   Step 2: 对每个 problem，判断是根因还是症状
   Step 3: 给出修复建议
   ```

3. **引用验证**
   - Prompt 要求："你的分析必须引用具体行号或 tool_id"
   - 后处理检查：引用的 id 是否真实存在

### 阶段 3：可视化增强（4-6 周）

**目标：让人能直观理解 LLM 的诊断。**

1. 甘特图上标记 LLM 指出的问题位置
2. 点击问题跳转原始日志
3. 简单因果图（只展示依赖关系，不展示完整图）
