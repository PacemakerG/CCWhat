# 自动诊断改进方向

参考 `agent-error-diagnosis-research.md` 的调研内容，结合当前项目现状整理。

---

## 优先级总表

| 优先级 | 改进点 | 问题 | 改动范围 | 成本 |
|------|------|------|------|------|
| P0 | findings 显式传给 LLM | LLM 在自己"发现"问题，而不是分析已知问题 | 改 `diagnosis_prompt.md` | 极低 |
| P0 | LLM 思考时间修正 | 把用户读回复/打字的时间算进了 LLM 思考，图表误导 | 改 `compute_phase_metrics` | 低 |
| P1 | 模式检测：重复失败重试 | `is_error → 同工具 → is_error` 这种死循环完全检测不到 | 在 `rule_findings` 加规则 | 中 |
| P1 | 模式检测：结果未被引用 | 工具调用了但结果没被后续用上，完全检测不到 | 在 `rule_findings` 加规则 | 中 |
| P2 | 分步 Prompt | LLM 跳过推理直接给结论 | 改 `diagnosis_prompt.md` | 低 |
| P2 | 阶段类型标注 | 阶段只有编号，不知道在规划/执行/验证哪个阶段 | 在 `build_phases` 加分类逻辑 | 中 |
| P3 | 甘特图标红 error | 要点进去看才知道哪里出错了 | 前端改动 | 中 |
| P3 | 工具依赖图 | 错误传播链检测不到 | 新增图结构 | 高 |

**P0 是现在必须做的：**
- **findings 传给 LLM**：改一个 md 文件就能做，收益立竿见影
- **LLM 思考时间**：当前图表数据是错的，会误导用户判断，属于数据准确性 bug

P1 填的是规则层最大的空白，做完后诊断覆盖的问题类型翻倍。P2 之后可以按需排期。

## 一、当前做了什么 → 对应哪些局限

### 规则提取层（core.py）

| 当前在做 | 做法 | 局限 |
|---------|------|------|
| 工具调用配对 | 按 `tool_use_id` 配对 use/result，算 `duration_ms`，标 `is_error` / `missing_result` | 只知道"这次调用耗时多少、有没有报错"，不知道这次调用和前后调用有什么关系 |
| 阶段划分 | 按 Skill 调用或用户消息切阶段 | 只知道"这是第几个阶段"，不知道这个阶段是在规划、执行还是验证，问题性质不清楚 |
| 时间拆分 | `wall = tool_exec + llm_think + human_idle`，10 分钟为阈值 | 10 分钟是拍脑袋的经验值，对长时间 session 可能偏低；三类时间之外的细节（如 LLM 思考了 8 分钟但只调了一个简单工具）看不出来 |
| 规则诊断 | 4 条阈值规则：耗时高、等待长、工具失败、高频调用 | 只能发现"量大"的问题，发现不了"模式"型问题——比如重复失败重试、工具结果没被用上、错误从工具 A 传播到工具 B |

### 调模型层（pipeline.py + analyzer.py）

| 当前在做 | 做法 | 局限 |
|---------|------|------|
| 构建上下文 | 把阶段耗时、规则诊断、慢工具事件、subagent 摘要拼成 Markdown，截断到 60k 字符 | findings 混在 Markdown 表格里，LLM 要自己从表格重新"发现"问题，而不是针对已知可疑点深入分析 |
| Prompt 策略 | 固定模板，要求输出"执行概要 + 主要问题 + 优化优先级" | 一次性输出所有内容，LLM 容易跳过推理直接给结论；没有强制"先列问题→再判断根因→最后给建议"的分步过程 |
| 工具输入传递 | input 字段按工具类型提取关键字段后截断到 500 字符 | LLM 看不到完整的工具参数，遇到复杂命令或长路径时分析不准 |

## 二、规则提取层怎么改进

### 改进 1：补充模式检测（填补最大空白）

当前 4 条规则全是"量"的判断（时间长不长、次数多不多），加入"序列模式"检测：

**重复失败重试**
- 检测：`is_error` → 紧跟同名工具 → 再次 `is_error`
- 意义：说明错误没有被修复就重试，是无效循环

**重复调用同参数**
- 检测：相同 `tool_name + input_summary`，在时序上连续出现 3 次以上
- 意义：可能是死循环，或 LLM 没有利用上一次的结果

**工具结果未被引用**
- 检测：扫 `content_summary` 的关键片段（文件路径、函数名），检查后续 5 条调用的 `input_summary` 是否出现
- 意义：这次工具调用的结果根本没被用上，是多余调用

**实现位置**：在 `rule_findings()` 里新增，产出格式和现有 finding 一致（`level / title / detail / phase_id`）。

### 改进 2：阶段类型标注

当前阶段只有 `source`（skill / user_turn / inferred），不知道阶段在做什么。

按阶段内工具占比打类型标签：

| 阶段类型 | 判断依据 | 典型问题 |
|---------|---------|---------|
| 规划阶段 | Skill / Agent 调用 > 50% | 目标理解偏、分解不合理 |
| 执行阶段 | Bash / Read / Edit 密集 | 命令错误、文件操作失败 |
| 验证阶段 | Bash 内含测试关键词（pytest、test、check） | 验证不充分 |
| 修复阶段 | Edit 后紧跟 Bash 测试 | 修复后没有验证 |

标注后可在 findings 的 `detail` 里带上阶段类型，让诊断更具体。

### 改进 3：放宽 input_summary 截断长度（低成本）

当前工具输入截断到 500 字符，Bash 的长命令、Edit 的大段内容都被截掉了。对规则匹配（模式检测、引用检测）影响较大。建议：

- Bash：保留完整 `command`（不截断，命令通常不超过 2000 字符）
- 其他工具：按实际需要调整，不强制 500

## 三、调模型层怎么改进

### 改进 1：把 findings 作为结构化输入显式传给 LLM（优先级最高，成本最低）

**现状**：findings 混在 Markdown 表格的"规则诊断"一节，LLM 需要自己从文字里识别哪些是已知问题。

**改法**：在 `diagnosis_prompt.md` 里加一段，把 findings 单独列出：

```
以下是程序规则层已检测到的可疑点，请以这些为起点展开分析，
重点回答"为什么会这样"和"怎么改"，不要重新发现问题：

[high] 阶段耗时较高：brainstorming add dark mode — 有效耗时 45m，工具 30m，LLM 15m
[high] 工具调用出现失败 — 共 3 次，主要工具：Edit, Bash
[medium] 存在长时间等待 — 人工等待 12m
```

**效果**：LLM 从"自己找问题"变成"针对已知问题分析根因"，输出更聚焦、更有深度。

### 改进 2：分步 Prompt

**现状**：一次性要求 LLM 输出执行概要 + 主要问题 + 优先级，容易跳过推理直接给结论。

**改法**：在 prompt 里明确要求分步思考：

```
请按以下步骤分析，每步的结论作为下一步的输入：
Step 1：列出所有可疑点（以规则检测结果为准）
Step 2：对每个可疑点，判断是根因还是症状
Step 3：针对根因给出可执行的建议
```

**效果**：强制推理链，减少"看起来合理但没有逻辑支撑"的结论。

### 改进 3：引用验证（后处理）

要求 LLM 在分析中必须引用具体的 `phase_id` 或 `tool_use_id`，输出后用代码检查这些 ID 是否真实存在于数据中。不存在的引用说明 LLM 在编造，可以标记或过滤。

## 四、可以新加入的能力

### 工具依赖图（参考 AgentTrace）

当前工具调用之间完全孤立，不知道工具 B 是否依赖了工具 A 的结果。

```
Read(file.py) 返回内容
    ↓ 被引用
Bash(grep "function_name" file.py) 的参数里出现了 file.py
    ↓ 出错
Edit(file.py) 也出错   ← 错误从 Read 开始传播
```

实现思路：
1. 扫 `content_summary` 里的关键片段（文件路径、函数名、变量名）
2. 检查后续工具调用的 `input_summary` 是否包含这些片段
3. 建立 `depends_on` 关系，配合 `is_error` 找传播链

当前 `content_summary` 截断到 500 字符，匹配覆盖率有限，建议先做规则模式检测再做依赖图。

### 步骤质量评分（参考 AgentProcessBench）

对每次工具调用打一个 0-100 的质量分：

```python
score = (
    (参数是否合理，非空非重复  ? 25 : 0) +
    (结果是否被后续引用        ? 25 : 0) +
    (耗时是否在合理范围内      ? 25 : 0) +
    (是否没有报错              ? 25 : 0)
)
```

低分工具调用可以单独列出，作为 findings 的补充维度，也可以作为新的 LLM 输入信号。
