# 模板驱动开发的实时任务证据与归因诊断重构计划

> **文档定位（2026-07-10）**：本文保留为 MVP 验证成功后的演进参考，不是当前实现范围。当前开发应以 [基于CC原始Session的OpenSpec归因诊断MVP计划.md](./基于CC原始Session的OpenSpec归因诊断MVP计划.md) 为准。本文中的 Action Contract、Action Run、Artifact/Outcome 图、Runtime Task、Dataset 和多模板适配等实体，只有在 MVP 暴露出明确且无法用更简单方法解决的问题时才进入后续 change；不得因为本文已描述就默认实施。

## 1. 结论

本项目的归因诊断不面向无流程约束的 Vibe Coding，而面向严格运行在 OpenSpec、Superpowers 等工作流模板中的 Coding Agent 任务。

因此，保留“粗图定位阶段、细图定位步骤”的总体方案：

```text
Workflow Template
  -> instantiate Action Run Graph（粗图）
  -> bind Event Evidence Graph（细图）

User/System Symptom
  -> route to Top-K Action candidates
  -> inspect evidence inside and across Action Runs
  -> produce evidence-backed hypotheses
  -> render diagnosis report
```

现有实现需要调整的不是两层图方向，而是两层图的语义：

1. 粗图不能只是固定阶段名称和线性先后关系，应升级为带输入、输出、完成条件和验证责任的 Workflow Contract Graph，并在每次任务中实例化为 Action Run Graph。
2. 细图不能只是 Tool Use 时间线，应升级为 Event Evidence Graph，包含 Event、Artifact、Requirement、Claim、Outcome 等证据对象及其可追溯关系。
3. 用户反馈只用于描述可观察 symptom，不应在语义分类阶段直接猜测 root cause。
4. symptom router 输出 Top-K Action 候选，不输出唯一责任节点；真正的归因结论来自后续证据检索和假设比较。
5. LLM 应用于自然语言理解、语义对齐和假设审阅；确定性日志关系、流程状态和证据引用必须由程序构建。
6. 不再把所有信号压缩成一个看似精确的 `0..100` 根因分数。输出支持证据、反证、不确定性和下一步验证。

## 2. 适用范围与前提

### 2.1 适用场景

- Coding Agent 明确运行在某个已知工作流模板下。
- 系统能识别模板，例如 `openspec`、`superpowers`。
- 模板规定了阶段、允许的转换、预期产物或验证责任。
- 系统能绑定任务边界与原始 Session/Trace。
- 用户反馈、测试结果或其他 evaluator 至少提供一种 outcome 线索。

### 2.2 不承诺的能力

- 不从完全无模板、无 outcome、无用户反馈的任意 Session 中证明真实根因。
- 不把时间先后直接解释为因果关系。
- 不把 LLM 的单次判断当作确定事实。
- 不保证只输出一个“罪魁祸首”；复杂失败可以同时有主要原因和促成原因。
- 不恢复依赖实时 Hook 的逐步 Git diff。最终 `task.diff` 仍表示任务边界内的仓库最终变化，行为过程从原始 Agent 日志事后抽取。

## 3. 核心术语

### 3.1 Workflow Template

某类开发流程的静态规范，例如 OpenSpec：

```text
proposal -> specs -> design -> tasks -> apply -> verify -> archive
```

Template 描述“应该怎样执行”，不是本次任务的实际执行记录。

### 3.2 Action Definition

Template 中某个阶段的契约定义。每个 Action 至少声明：

- `type`：阶段类型。
- `required_if`：在什么生命周期或条件下必须执行。
- `inputs`：应消费哪些上游产物。
- `outputs`：应产生哪些产物。
- `completion_evidence`：怎样证明该阶段完成。
- `validation_responsibilities`：该阶段承担什么验证责任。
- `allowed_transitions`：允许进入哪些后继阶段。
- `symptom_priors`：哪些 symptom 通常与该阶段相关，只作为路由先验。

### 3.3 Action Run

Action Definition 在一次真实任务中的执行实例。例如：

```text
Apply#1 -> Verify#1(failed) -> Apply#2 -> Verify#2(passed)
```

同一种 Action 可以有多个 Run，不能把所有 Apply 或 Verify 事件永久聚合到一个静态节点中。

### 3.4 Event Evidence Graph

一次任务内的事实证据图。它不只包含 Tool Use，还包含工具结果、文件/产物版本、需求、声明和验证结果。

### 3.5 Symptom

用户或系统可观察到的问题，例如“测试失败”“功能不符合需求”“产物缺失”。Symptom 描述发生了什么，不描述为什么发生。

### 3.6 Cause Hypothesis

系统结合粗图、细图和 outcome 证据生成的原因假设，例如“Apply#2 中的 Edit E42 实现了错误条件”。Hypothesis 必须包含支持证据、反证、缺失证据和建议验证动作。

## 4. 目标总体架构

```text
                        +----------------------+
                        |  Workflow Template   |
                        | OpenSpec/Superpowers |
                        +----------+-----------+
                                   |
                                   | instantiate
                                   v
+----------------+       +----------------------+       +----------------------+
| Runtime Task   |------>|  Action Run Graph    |<------| Action/Event Mapping |
| start/finish   |       |      粗图            |       +----------+-----------+
+--------+-------+       +----------+-----------+                  |
         |                          | contains / consumes / produces|
         | bind trace               v                              |
         |                +----------------------+                  |
         +--------------->| Event Evidence Graph |<-----------------+
                          |      细图            |
                          +----------+-----------+
                                     |
                 +-------------------+-------------------+
                 |                                       |
                 v                                       v
        +------------------+                    +------------------+
        | System Detectors |                    | User Feedback    |
        | error/missing/...|                    | Semantic Router  |
        +---------+--------+                    +---------+--------+
                  +-------------------+-------------------+
                                      v
                             +------------------+
                             | Symptom Reports  |
                             +---------+--------+
                                       |
                                       | Top-K Action routing
                                       v
                             +------------------+
                             | Evidence Search  |
                             | & Hypotheses     |
                             +---------+--------+
                                       v
                             +------------------+
                             | Diagnosis Report |
                             +------------------+
```

对用户仍展示两张图：

- 粗图：Action Run Graph，用于理解流程阶段、状态和责任区。
- 细图：Event Evidence Graph，用于查看具体执行步骤和证据关系。

Workflow Template 是内部规范层，可以在粗图中作为背景或折叠视图，不需要单独成为第三张主图。

## 5. 粗图改进方案

### 5.1 从固定七节点升级为模板实例图

当前固定 OpenSpec 七节点可以保留为第一版 `OpenSpecWorkflowTemplate`，但不再直接承载本次运行状态。

目标结构：

```json
{
  "template_id": "openspec-v1",
  "actions": [
    {
      "type": "apply",
      "required_if": "change_status in ['in_progress', 'implemented']",
      "inputs": ["tasks", "specs", "design"],
      "outputs": ["repository_change"],
      "completion_evidence": ["mapped_code_change"],
      "validation_responsibilities": [],
      "allowed_transitions": ["verify"]
    },
    {
      "type": "verify",
      "required_if": "implementation_exists",
      "inputs": ["repository_change", "acceptance_criteria"],
      "outputs": ["validation_outcome"],
      "completion_evidence": ["completed_validation_result"],
      "validation_responsibilities": ["tests", "openspec_validate"],
      "allowed_transitions": ["apply", "archive"]
    }
  ]
}
```

### 5.2 Action Run 节点

每次真实进入某个阶段时创建或推断一个 Action Run：

```json
{
  "action_run_id": "AR-apply-2",
  "action_type": "apply",
  "ordinal": 2,
  "status": "completed",
  "started_at": "...",
  "ended_at": "...",
  "event_ids": ["E38", "E39", "E42"],
  "input_artifact_ids": ["ART-spec-3", "ART-tasks-2"],
  "output_artifact_ids": ["ART-src-7"],
  "completion_evidence_refs": ["event:E42", "task-diff:H3"],
  "mapping_confidence": "high"
}
```

### 5.3 粗图边类型

粗图需要区分规范关系和真实执行关系：

| 边类型 | 含义 | 来源 |
|---|---|---|
| `template_precedes` | 模板规定的阶段先后 | Workflow Template |
| `run_transition` | 本次任务真实从一个 Run 进入另一个 Run | Event 顺序/显式 Skill |
| `consumes` | Action Run 消费某个 Artifact/Requirement | observed 或 inferred |
| `produces` | Action Run 产生某个 Artifact/Outcome | observed 或 inferred |
| `revises` | 后续 Run 修订前一个 Run 的产物 | artifact version |
| `validates` | Verify Run 验证某个 Apply Run 或 Artifact | command scope/outcome |

`template_precedes` 不能用于证明因果，只能用于流程合规和候选路由。

### 5.4 Action Run 状态

避免继续把“没有观察到”直接写成 missing/skipped：

```text
not_required_yet  当前生命周期尚不要求
not_observed      没有采集到充分证据
in_progress       已进入但未完成
completed         有完成证据
failed            有失败 outcome
skipped           有证据表明绕过了 required Action
unknown           证据冲突或覆盖不足
```

`archive` 只在 change 已满足归档条件时 required。正在实现的 change 不应因尚未 archive 自动成为高严重度问题。

### 5.5 Event 到 Action Run 的映射

映射应允许：

- 一个 Event 属于一个主要 Action Run。
- 一个 Event 关联多个辅助 Action Run，例如 Apply 阶段读取 spec。
- 显式 Skill/command/path 提供高置信映射。
- 时序窗口和工具组合提供中低置信映射。
- 无法映射的 Event 保留为 `unassigned`，不创建游离且不可达的伪 Action。

映射输出：

```json
{
  "event_id": "E42",
  "primary_action_run_id": "AR-apply-2",
  "related_action_run_ids": ["AR-specs-1"],
  "reason": "edited source file during active apply run",
  "confidence": "high"
}
```

### 5.6 多模板扩展接口

OpenSpec 和 Superpowers 通过模板适配器提供：

```text
WorkflowTemplateAdapter
  - detect(session/task) -> template_id
  - definitions() -> ActionDefinition[]
  - recognize_action_runs(events) -> ActionRun[]
  - map_event(event, context) -> ActionMapping[]
  - evaluate_contract(action_run, evidence) -> WorkflowFinding[]
  - symptom_priors(symptom_type) -> ActionPrior[]
```

第一版只实现 OpenSpec，接口先稳定，后续再增加 Superpowers，避免把七节点硬编码扩散到 scorer、Viewer 和输出模型。

## 6. 细图重新设计

### 6.1 从 Event Timeline 升级为 Evidence Graph

细图的目标不是展示“发生过哪些 Tool Use”，而是回答：

- 哪个步骤读取了什么信息？
- 哪个步骤修改了什么产物？
- 哪个命令验证了哪个版本？
- 哪个结果支持或反驳了 final claim？
- 用户反馈所指的错误产物由哪些步骤产生？

因此细图包含两类节点。

#### 执行节点

- `user_message`
- `assistant_message`
- `tool_call`
- `tool_result`
- `command`
- `command_result`
- `file_read`
- `file_edit`
- `final_claim`
- `agent_dispatch`

#### 证据实体节点

- `requirement`
- `artifact`
- `artifact_version`
- `diff_hunk`
- `validation_outcome`
- `user_feedback`
- `external_evaluation`

Artifact/Outcome 节点是 semantic symptom 与 Tool Event 之间的桥梁。例如“按钮点击行为错误”首先关联到 UI artifact/requirement，再回溯产生它的 edit 和所属 Apply Run。

### 6.2 节点最小字段

```json
{
  "node_id": "E42",
  "node_type": "file_edit",
  "timestamp": "...",
  "agent_id": "main",
  "turn_index": 8,
  "tool_call_id": "toolu_123",
  "action_run_id": "AR-apply-2",
  "summary": "Edit viewer/button.js",
  "data": {},
  "raw_ref": {
    "source": "claude_session",
    "session_id": "...",
    "line": 142
  }
}
```

要求：

- `node_id` 全图唯一；一条原始日志包含多个 Tool Use 时必须生成不同节点 ID。
- Tool Call 和 Tool Result 必须通过稳定 `tool_call_id` 配对。
- 原始证据引用不得在构图时丢失。
- 命令结果保留 exit code、stdout/stderr 摘要和完整 raw reference。
- `task.diff` hunk 可作为最终仓库状态证据，但不强行绑定到单个 Event。

### 6.3 细图边类型

#### 直接观察边

| 边类型 | 示例 |
|---|---|
| `next_in_agent` | 同一 Agent 中的事件顺序 |
| `tool_result_of` | Tool Result -> Tool Call |
| `reads` | Read Event -> Artifact Version |
| `writes` | Edit Event -> Artifact Version |
| `produces_result` | Command -> Command Result |
| `reports_outcome` | Command Result -> Validation Outcome |
| `claims` | Final Message -> Claim |
| `belongs_to` | Event -> Action Run |
| `spawned` | Agent Dispatch -> Subagent Event |

#### 推断边

| 边类型 | 示例 |
|---|---|
| `likely_informed_by` | Edit 可能使用了此前 Read 结果 |
| `likely_validates` | 测试命令可能覆盖某个 Artifact Version |
| `supports` | 验证结果支持某个 Claim |
| `contradicts` | Outcome/Feedback 反驳 Claim 或 Artifact |
| `likely_contributes_to` | Edit 可能促成失败 Outcome |

每条边必须携带：

```json
{
  "edge_id": "EDGE-77",
  "type": "likely_validates",
  "from": "CMD-17",
  "to": "ART-src-7",
  "provenance": "rule:test-command-file-scope-v1",
  "evidence_refs": ["event:E57", "artifact:ART-src-7"],
  "confidence": "medium",
  "observed": false
}
```

时间相邻只生成 `next_in_agent`，不能自动生成因果边。

### 6.4 细图视图裁剪

完整 Evidence Graph 可以跨越多个 Action Run。Viewer 钻入某个粗节点时，显示：

1. 该 Action Run 的内部 Event。
2. 它读取的上游 Artifact/Requirement。
3. 它产生的下游 Artifact/Outcome。
4. 与当前 symptom 相关的跨 Action 边。

这样既保留局部可读性，又不会切断“Specs 误解 -> Apply 错误实现 -> Verify 漏检”这样的跨阶段链路。

## 7. 用户反馈与 Symptom 设计

### 7.1 Diagnosis Request

用户反馈不应只是一段裸文本，应封装成可扩展请求：

```json
{
  "task_id": "task-123",
  "source": "user_report",
  "report_text": "按钮样式改了，但点击后仍然跳到错误页面",
  "expected": "点击后进入详情页",
  "observed": "点击后进入列表页",
  "artifact_hints": ["button", "routing"],
  "event_hints": [],
  "attachments": [],
  "created_at": "..."
}
```

前端第一版只要求 `report_text`，其他字段可由用户补充、系统提取或后续追问。

### 7.2 Symptom 分类只描述现象

第一版建议：

```text
workflow_violation
validation_failed
execution_error
missing_output
wrong_output
incomplete_output
regression
unsupported_claim
performance_or_loop
unknown
```

不要把以下原因假设放进 symptom taxonomy：

```text
bad_edit
insufficient_context
misunderstood_requirement
missing_verification
ignored_error
```

它们属于后续 `cause_family` 或 hypothesis。

### 7.3 Symptom Route 输出

Router 输出多标签 symptom、受影响对象和 Top-K Action 候选：

```json
{
  "symptoms": [
    {
      "type": "wrong_output",
      "confidence": "high",
      "expected": "进入详情页",
      "observed": "进入列表页",
      "query_terms": ["button", "routing", "详情页", "列表页"],
      "affected_artifact_hints": ["frontend routing"],
      "evidence_refs": ["feedback:UF-1"]
    }
  ],
  "action_candidates": [
    {
      "action_type": "apply",
      "prior": "high",
      "reasons": ["wrong_output commonly originates in implementation"]
    },
    {
      "action_type": "verify",
      "prior": "high",
      "reasons": ["incorrect behavior may have escaped validation"]
    },
    {
      "action_type": "specs",
      "prior": "medium",
      "reasons": ["expected behavior may be ambiguous or misread"]
    }
  ]
}
```

`prior` 只用于召回和搜索顺序，不是根因置信度。

### 7.4 系统自动 Symptom

以下结构化问题不需要 LLM：

- command/tool result 明确失败。
- required artifact 明确缺失。
- required Action 在适用生命周期内被跳过。
- final claim 前没有任何完成的验证结果。
- 测试失败后直接 final claim。
- 重复相同失败调用。
- task.diff 与“没有修改”等声明直接冲突。

自动 symptom 和用户 symptom 可以合并，不能互相覆盖。

## 8. 是否调用大模型

### 8.1 结论：采用混合方案

需要 LLM，但只在语义问题上使用。整体原则：

```text
规则负责事实
LLM 负责语义
图负责约束
报告负责表达不确定性
```

### 8.2 不调用 LLM 的部分

- Template/Action 状态计算。
- Event 标准化和 Tool Call/Result 配对。
- 文件、命令、时间、task.diff、exit code 等事实关系。
- 显式 failure detector。
- 图遍历、证据检索和 ID 校验。
- LLM 输出引用是否合法的后处理。

### 8.3 调用 LLM 的部分

#### 调用一：用户反馈语义解析

输入：

- 用户反馈文本。
- expected/observed（如果有）。
- Workflow Template 中的 Action Definition 摘要。
- 当前任务 artifact/file 摘要。

输出严格 JSON：

- symptom 多标签分类。
- expected/observed 提取。
- affected artifact/query terms。
- Top-K Action 类型及路由理由。
- 是否需要用户补充信息。

LLM 此时不能输出具体 root cause Event。

#### 调用二：候选证据语义审阅

程序先检索 Top-K Action Run 及相关 Evidence 子图，再把有限候选交给 LLM：

- 用户 symptom。
- 相关 requirement/spec 片段。
- candidate Event 的输入输出摘要。
- artifact diff/hunk。
- validation outcome。
- 已有规则 findings。

LLM 输出：

- hypothesis statement。
- supporting/refuting evidence ID。
- cause family。
- missing evidence。
- next verification。

LLM 只能引用输入中存在的 ID；后处理发现虚构 ID 时，该 hypothesis 失效或降级。

### 8.4 LLM 失败与低置信度降级

- LLM 不可用：保留系统自动 symptom、Workflow Findings 和规则证据链。
- 反馈过于模糊：输出 `needs_clarification`，不要强行选 Action。
- 没有 outcome/expected：允许诊断 explicit failure，但对 silent wrong output 输出 `insufficient_outcome_evidence`。
- 多个候选证据相互冲突：并列输出 hypotheses，不强制合并为一个结论。

## 9. 粗到细的诊断流程

### 9.1 主流程

```text
1. Resolve runtime task and source binding
2. Detect Workflow Template
3. Instantiate Action Runs
4. Build Event Evidence Graph
5. Ingest system outcome and/or user feedback
6. Detect/parse Symptoms
7. Route Symptoms to Top-K Action candidates
8. Select concrete Action Runs
9. Retrieve local and cross-Action evidence subgraphs
10. Generate candidate hypotheses from deterministic signals
11. Optionally ask LLM to review semantic consistency
12. Validate all evidence references
13. Rank hypotheses by evidence tier
14. Render diagnosis report
```

### 9.2 候选生成与排序

候选必须至少满足一项：

- 位于 symptom 相关 Action Run 中，并命中 artifact/query terms。
- 通过 observed/inferred evidence edge 连接到失败 Outcome。
- 其输出与 Requirement/User Feedback 存在语义矛盾。
- 其后续验证未覆盖对应 Artifact/行为。
- 它是系统 detector 明确指出的异常步骤。

信号分为独立家族：

```text
workflow_contract
execution_result
artifact_provenance
semantic_consistency
verification_coverage
claim_support
reference_trace_delta
```

输出保留 `supports / contradicts / unknown`。不把同一家族的多个相关规则重复累计。

排序等级：

```text
confirmed   有直接失败证据或隔离复验确认
strong      多个独立信号族支持，且无强反证
plausible   有一条合理证据链，但仍需验证
weak        主要依赖路由先验或时间接近
insufficient 无法形成可审查证据链
```

等级内部可以使用确定性排序键，例如：

```text
direct outcome link
> semantic contradiction with requirement
> independent signal family count
> observed edge count
> inferred edge count
> causal path length
> temporal distance
```

如实现内部仍需要 numeric rank，字段必须叫 `ranking_score`，不能显示为 root-cause probability，也不能直接映射为 high/medium/low confidence。

## 10. 诊断结果与报告

### 10.1 结构化结果

```json
{
```

### 10.2 用户报告结构

报告按以下顺序呈现：

1. 用户问题理解：expected、observed、symptom。
2. 证据覆盖情况：哪些数据完整，哪些缺失。
3. 最可疑流程环节：Top-K Action Run 及理由。
4. 主要原因假设：具体 Event、Artifact 和证据链。
5. 促成原因：例如 Verify 漏检、Specs 歧义。
6. 反证与替代解释。
7. 下一步验证动作。
8. 粗图和细图跳转链接。

报告使用“支持程度”而不是“确定根因”。只有经过隔离复验或明确 evaluator 证据时，才使用接近确定性的表述。

## 11. 实时任务证据绑定

粗细图可信的前提仍然是任务证据稳定绑定。

实时任务包建议：

```text
tasks/<task-id>/
  task.json
  task.diff
  task_evidence.json
```

`task_evidence.json` 至少记录：

- schema version。
- task/run/workspace/template identifier。
- start/end 时间与 tree hash。
- session/trace identifier。
- task event range 或 event IDs。
- raw log references。
- task.diff 路径及 completeness。
- outcome/evaluator references。
- evidence availability。

`task.diff` 表示 start/finish 边界内的最终仓库状态变化；原始 Session 表示 Agent 行为。二者交叉校验，但不伪造逐 hunk 的 Event 归属。


现有组件处理建议：

| 现有组件 | 处理方式 |
|---|---|
| fixed OpenSpec actions | 迁入 `workflow_templates/openspec.py`，升级为 Action Definition |

| `EventGraph` | 升级为 Evidence Graph，保留兼容序列化层 |

## 13. 分阶段实施计划

### Phase 0：冻结术语和输出契约

1. 明确 Template、Action Definition、Action Run、Evidence Node、Symptom、Hypothesis。
2. 定义新 JSON schema 和向后兼容策略。
3. 将 workflow compliance 与 attribution diagnosis 分成独立结果域。

完成条件：后续模块不会再混用 symptom、cause、Action template 和 Action instance。

### Phase 1：重构粗图

1. 把固定 OpenSpec 七节点迁移为 `OpenSpecWorkflowTemplate`。
2. 为每个 Action 增加 contract。
3. 从 Session Event 实例化 Action Runs，支持 Apply/Verify 循环。
4. 引入新状态模型和条件性 required。
5. Viewer 粗图显示 Run、状态、输入输出和证据数量。

完成条件：同一任务中能够区分 `Apply#1/Verify#1/Apply#2/Verify#2`，且未归档的进行中 change 不会误报 archive failure。

### Phase 2：重构细图

1. 修复跨 Agent 的唯一 Event ID。
2. 保留 raw reference、Tool input/result、exit status。
3. 增加 Artifact Version、Requirement、Claim、Outcome 节点。
4. 增加 observed/inferred evidence edges。
5. 建立 Action Run 与 Evidence Graph 的双向映射。
6. Viewer 支持按 Action Run 裁剪细图并保留跨阶段证据链。

完成条件：用户能从粗节点进入具体 Event，并从 Event 回到原始日志、artifact/diff 和 outcome。

### Phase 3：用户反馈与 Symptom Router

1. 定义 `DiagnosisRequest` 和反馈存储。
2. 实现 deterministic symptom detectors。
3. 接入受约束的 LLM 反馈解析。
4. 输出多标签 symptom、affected artifact 和 Top-K Action candidates。
5. 增加 `needs_clarification` 和 `insufficient_outcome_evidence`。

完成条件：相同用户反馈不会被直接分类为 `bad_edit` 等原因；Router 只做现象解析和候选召回。

### Phase 4：证据检索与归因假设

1. 从 Action candidates 选择具体 Action Runs。
2. 检索局部及跨 Action Evidence 子图。
3. 生成支持/反证/未知信号矩阵。
4. 生成主要原因和促成原因 hypotheses。
5. 可选调用 LLM 做语义一致性审阅。
6. 对所有 LLM evidence ID 做后处理校验。

完成条件：每条 hypothesis 都能定位到真实 Action Run、Event、Artifact 或 Outcome；证据不足时明确拒绝归因。

### Phase 5：报告、评测与第二模板

1. Viewer 展示 symptom -> Action -> Event -> Outcome 诊断链。
2. 增加用户确认、驳回和补充证据入口。
3. 建立诊断 fixture 与评测指标。
4. 在 OpenSpec 稳定后接入 Superpowers template adapter。

完成条件：OpenSpec 端到端诊断通过验收，并证明模板适配器不依赖固定七节点硬编码。

## 14. 测试与验收矩阵

### 14.1 图结构测试

- Event/Artifact/Outcome 节点 ID 全局唯一。
- 无悬空边。
- Tool Call/Result 正确配对。
- raw reference 可回到原始日志。
- 一个 Action Type 可以实例化多个 Run。
- Event 可主映射一个 Run，并关联其他 Run。
- inferred edge 必须带 provenance 和置信来源。

### 14.2 Workflow 测试

- 正常 OpenSpec 全流程。
- Apply/Verify 多轮循环。
- 进行中 change 尚未 archive。
- required Action 被明确跳过。
- 只读取 artifact 不等于完成对应 Action。
- session evidence 缺失时状态为 `not_observed/unknown`，不是自动 `skipped`。

### 14.3 Symptom 路由测试

- 显式 validation failure 不调用 LLM 也能路由。
- wrong output 路由到 Apply/Verify/Specs Top-K。
- 一段反馈包含多个 symptom。
- 模糊反馈返回 clarification。
- LLM 返回未知 Action/Event ID 时被拒绝。
- LLM 不可用时规则输出仍可用。

### 14.4 归因场景测试

- 某次 Edit 直接导致测试失败。
- 测试原本 flaky，不能自动归因到最近 Edit。
- Specs 正确、Apply 实现错误、Verify 漏检。
- Specs 自身歧义导致后续一致地实现了错误目标。
- Tool error 被忽略后直接 claim 完成。
- task.diff 与 final claim 冲突。
- silent wrong output 有用户 expected/observed。
- silent wrong output 没有 outcome oracle，系统应 abstain。
- 并发工作区修改或 ignored file 导致证据不完整。

### 14.5 评测指标

- 图关系准确率与 evidence reference 有效率。
- symptom 分类 precision/recall。
- Action Top-K recall。
- root-cause Event Top-K recall / MRR。
- LLM 引用合法率。
- unsupported hypothesis rate。
- abstention coverage：证据不足时是否正确拒绝。
- 人工评审的诊断可用性。

测试不再只断言“最高分超过 50”，必须断言正确 Action Run、Event 或证据链进入 Top-K，同时关键反例不会被误判。

## 15. 对当前 OpenSpec change 的处理建议

当前 `add-symptom-routed-graph-attribution` 不应继续按原 tasks 直接实现。建议以本计划为依据重写或拆分为：

1. `refactor-workflow-action-run-graph`
2. `build-event-evidence-graph`
3. `add-feedback-routed-evidence-attribution`

如果保留一个 change，也必须调整为上述 Phase 1-4 的顺序，并删除以下要求：

- 所有 symptom 必须先沿固定七节点 DAG 反向遍历。
- 用户反馈只能分类成唯一 symptom/唯一 anchor Action。
- Action/Event 使用通用分加 symptom 权重得到对外 `0..100` 根因分。
- 只根据 Action 缺少 mapped event 就判定 skipped。
- Event 只在一个粗节点内部分析，不允许跨 Action 证据链。

## 16. 最终设计原则

```text
模板提供诊断先验，但不替代实际证据。
粗图负责流程契约、状态和候选路由。
细图负责步骤、产物、结果和证据关系。
Symptom 描述现象，Hypothesis 解释原因。
Router 做 Top-K 召回，不提前裁决根因。
规则构建事实，LLM 处理语义。
每个结论都必须可回到真实证据。
证据不足时拒绝归因，比输出虚假高分更正确。
```

这套架构保留原有“先粗后细”的核心思路，同时使它能够在 OpenSpec、Superpowers 等严格模板流程中稳定扩展，并对 explicit failure 与有 outcome 依据的 silent failure 生成可审查的诊断报告。
