# 反向归因打分机制问题分析与建议

## 背景

当前 `add-symptom-routed-graph-attribution` 的设计采用了 symptom 分类 → Action 级反向遍历 → Event 级打分 → causal chain 输出的归因路线。但设计中的 scoring 机制存在一些根本性问题，本文记录这些问题的分析。

---

## 问题一：系统规则只覆盖已知错误，无法处理 silent failure

### 设计中的规则示例

```
validation_failed → 给失败命令前最近的 edit 加 30 分
unsupported_final_claim → 缺 verify 则 claim 加 35 分
tool_or_command_error_ignored → error result 后继续执行加 25 分
```

### 问题

这些规则都预设了**"我知道问题长什么样"**——比如"验证失败了，那肯定是验证前那次改代码搞的"。这在简单的、有信号的 failure 场景下成立。

但 silent failure 恰恰是**你不知道的那一类**：

- 模型每一步都没报错，最终产物就是不对
- 没有 error token、没有 assertion、没有缺失的 artifact
- 可能模型在 proposal 阶段就理解错了需求，后面每一步都是"正确地在做一件错的事"

对这种情况，任何预设规则都无效——因为你事先不知道哪一类操作会导致什么错误。

### 本质矛盾

| 维度 | 有信号的 failure | 无信号的 silent failure |
|------|-----------------|------------------------|
| 有没有线索 | ✅ 有（error、missing、crash） | ❌ 没有 |
| 系统规则是否有效 | ✅ 有效 | ❌ 无效 |
| 需要什么 | 匹配已知模式 | 发现未知模式 |

**结论：** 这套打分机制只覆盖了一半场景。对 silent failure 需要另一套策略。

---

## 问题二：打分值没有物理意义，无法校准

```
score += max(0, 25 - max(0, distance - 1) * 5)  # 距离衰减
score += 40 if action.status == "missing"          # 缺失+40
```

### 问题

- 85 分和 72 分的区别是什么？没人知道。
- 这些分数没有校准手段——你不能拿一个 labeled dataset 来调参，因为 silent failure 的 label 本身就很模糊。
- 分数排序不一定反映真实根因排序。你只是看着分数排序，觉得"好像有道理"。

这和之前 segment 打分遇到的困境是一样的。

---

## 问题三：规则越细，误判越多

每加一条规则，就在"覆盖新场景"和"误判既有场景"之间做 tradeoff。

以 `validation_failed → 给失败命令前最近 edit 加 30 分` 为例：

| 场景 | 规则命中？ | 实际根因 |
|------|-----------|---------|
| 改了一个 typo 导致测试挂 | ✅ 对 | 改 typo 那个 edit |
| 测试本来就有 flaky，跟 edit 无关 | ❌ 误判 | 环境问题 |
| 没改代码，但 spec 写错了导致验证逻辑不对 | ❌ 误判 | spec 阶段的错误 |
| 模型在 edit 之前读错了一个关键文件 | ❌ 漏判 | read 阶段的错误 |

这些 tradeoff 没有自动调优手段，只能靠人反复调参。

---

## 建议方案

### 建议一：用多信号投票代替单一加权公式

```
不是：event_42 得分 86
而是：event_42 被以下信号指向
  ✅ 信号A：该 event 位于错误子图中
  ✅ 信号E：该 event 的产出与 spec 矛盾
  ❌ 信号C：该 event 被编辑后从未验证
  → 3/5 信号指向
```

好处：

- 每种信号是一个独立的 vote detector，互不影响
- 新加一种信号等于加一个投票器，不破坏既有投票
- 如果一个未知类型的 bug 命中了两三个信号，它自动就会被捞出来
- 不需要事先定义它属于哪类 symptom

### 建议二：用反事实推理代替打分

核心思路：不要问"哪个 Event 最可疑"，问"去掉这个 Event，失败的 trace 能不能变成成功的 trace？"

```
成功 trace：read spec → edit A → read test → edit B → pytest → all pass
失败 trace：read spec → edit A → edit B → pytest → 3 failed
                                           ↑ 没有 read test 这一步就是可疑点
```

如果能对齐成功和失败 trace 的 Event Graph，diff 就是诊断本身。

### 建议三：承认两种 failure 需要两套诊断策略

```
有信号的 failure（error、missing、crash）  ──→ 系统规则 + symptom routing 就够用
无信号的 failure（silent、wrong output）    ──→ 需要 outcome verification + trace 比对
```

不要在 silent failure 上硬套打分规则。用静默检测器去验证最终产出和 trace 的一致性。

### 建议四：优先保证 Graph 结构准确

不管打分怎么设计，以下**客观关系**比任何加权分数都重要：

- 谁先谁后（temporal edges）
- 谁读了谁（read→edit edges）
- 谁改了谁（edit→command edges）
- 谁报错了（error edges）
- 谁 claim 了什么（claim edges）

把这些结构呈现给人（或者 LLM），比系统自动给一个分数有用得多。
